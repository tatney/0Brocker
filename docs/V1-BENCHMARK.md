# 0Brocker v1 benchmark and implementation

Reviewed 1 October 2026. The product is a direct owner/resident/service-provider marketplace for Uganda, priced in UGX. The comparison below uses official product material. The tradeoffs are our design choices, not measured claims that a competitor fails its customers. We do not claim this test version matches entire enterprise platforms.

## Implemented behavior

- One shared visual system and five consistent main destinations: Home, Services, My home, Chat, Profile.
- Search terms and all chosen listing filters are intersected; changing rent/buy preserves other constraints.
- Maximum asking price and deterministic price sorting. Comparison labels monthly rent versus sale asking prices explicitly.
- Persistent saved searches, resident notes and checklists, scoped to the signed-in user.
- Posting requires an ownership declaration; plots post as sale/land and shared homes as rental/house. New posts have no fabricated reviews or automatic verification. Kampala is the default city; large UGX sale prices are accepted.
- Posted owner identity and declaration are persisted separately from independently verified status. Owner conversations have functional navigation and local persistence; no phone number is fabricated.
- Service hub and booking flow use the same provider records. Prices follow the selected provider; brokerage is zero. Custom scheduling uses Kampala UTC+3 and rejects past/invalid times.
- Selecting a payment method does not mark a booking paid. Payment simulation is explicitly labelled. Booking history uses current marketplace bookings and the signed-in customer.
- Reviews require the customer's paid booking; optional dimension ratings fall back to the actual overall rating, rather than inventing five stars. Duplicate submission is prevented by the reviewed lifecycle state.
- Admin workspace remains responsive and supports listing/provider verification, booking transitions, financial summaries and filtered CSV export. Live access requires a Supabase admin role. A separate server-authenticated test workspace has sample data only.

## Testing boundary and production gaps

The APK is an offline test app with seeded listings and providers. Requests, messages, saved searches and home notes are stored on the device. The Vercel test admin uses independent sample data stored in the browser; it is not synchronized with the APK. No money is transferred, providers are not dispatched and no real owner/property/background verification is performed.

Before a public launch: connect the mobile app to authenticated backend APIs and the same admin dataset; enforce owner/provider eligibility and verification evidence server-side; replace demo password hashing with managed authentication; scope all legacy wallet/chat/favourite data; add real uploads, moderation, reporting and dispute workflows; configure payment rails/webhooks; implement actual messaging, push reminders and geographic search; add lease/document management and accessible device-level acceptance tests. Launch criteria must include anti-broker checks, consent, local property/payment requirements and operational support. An ownership checkbox alone cannot enforce the no-broker policy in a live marketplace.
